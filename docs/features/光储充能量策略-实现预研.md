## 0. 一句话结论

SPEC 要建的"光储充能量策略层"**不需要从零造引擎**：后端 `backend/app/services/charging/` 已有一套抽象良好的充放电策略引擎（`ChargingStrategy` 基类 + `ChargingContext`/`ChargingDecision` + `StrategyEngine` 单例 + 光伏预测 + 储能优化器）。预研的核心结论是——**复用现有策略引擎抽象，把它从"单策略互斥选择"演进出"多策略并行仲裁"，并用 celery beat（已接入）做 15min 周期触发**。六张新表里只有"购电价模板"是真正新增语义，其余多为现有能力的持久化/流水化。

**为什么这是核心**：`ChargingContext`(strategy_base.py:28) 已经包含了 SPEC §7 步骤1 要读的**全部状态**——光伏(`pv_output_kw`)、储能(`battery_soc`/`battery_capacity_kwh`/`battery_available_kw`/`battery_temp_c`)、电网(`grid_price`/`grid_power_limit_kw`)、时段(`in_valley_period`)、车辆需求(`demand_power_kw`)。`ChargingDecision`(L53) 已经是 SPEC §7 步骤3 要下发的**三源功率分解**（`pv_power_kw`/`battery_power_kw`/`grid_power_kw` + `reconcile_source()`）。**SPEC 调度引擎的输入/输出契约，现有代码已基本具备。**

**关键缺口（复用 vs 扩展的分界线）**：
1. 现有是**单策略互斥选择**（`StrategyEngine.resolve` 选一个 mode 评估），SPEC §4 要**多策略并行 + 仲裁** → 需新增"仲裁层"。
2. 现有策略**参数硬编码**（如 `StorageOptimizer.PEAK_PRICE`/`VALLEY_PRICE` 是类常量，storage_optimizer.py 内），SPEC 要场站级可配 → 需 `station_energy_strategy` 表注入参数。
3. 现有 `grid_price` 是**运行时单一值**，SPEC 要**版本化价格曲线 + 省级模板** → 需 `energy_price_template`。
4. 现有引擎**无周期触发、无流水落库**（`ChargingDecision` 不持久化），SPEC 要 15min 周期 + `energy_flow_log` → 需 celery beat + 流水表。

### 1.3 分时电价（版本化模式可借鉴，但语义不同）

| 类 | 表 | 行号 | 关键字段 |

**关键判断**：现有 `EnergyPrice` 是**对客售价**（场站卖给车主的充电费），SPEC §8 的 `energy_price_template` 是**购电价**（场站从电网买电的成本）。**两者语义不同，不能直接复用同一张表**。但 `EnergyPrice` 的 `effective_date`/`expire_date`/`is_active` 三件套是现成的"生效区间"模式，新建购电价模板应**借鉴此模式**并补齐 SPEC §2.3 要求的 `version` 版本号、省份维度、季节区间。

⚠️ `TimeSlotDefinition.period_type` 带 `unique=True`(L55)，意味着**全局只有一套尖/峰/平/谷时段定义**，无法按省份/季节区分。这与 SPEC §5"省级模板"冲突 → 新模板必须自带时段明细子表（即 `energy_price_period`），不能复用 `time_slot_definitions`。

## 2. SPEC §8 六张新表字段设计草案

> 命名风格对齐：参考 `pricing_v2.py`/`charging_schedule.py` 的 `Column(... comment=...)` + `__table_args__ = (Index(...),)` 风格。
> **隔离契约**：新表统一用 `team_id` 外键（对齐 `station.py:38` 的 `team_id = Column(Integer, ForeignKey("teams.id"))` 与团队隔离契约），**不要**沿用 `charging_schedule.py` 的 `enterprise_id`（见 §6 风险）。
> **时间列惯例**：`created_at`/`updated_at`，`default=datetime.utcnow`（对齐 pricing_v2/charging_schedule）；时间序列字段用 `DateTime(timezone=True)`（对齐 telemetry_v2）。
> **PK 类型**：配置类表用 `Integer, primary_key, autoincrement`（对齐 pricing_v2）；流水表 `energy_flow_log` 数据量大，建议 `BigInteger`（对齐 telemetry_v2 的 Phase1 防溢出风格）。
> 以下均为**设计草案的字段清单**，非可执行代码。

## 4. 15min 调度引擎接入方案

### 4.1 两种接入路径对比

| 维度 | 方案A：celery beat 周期任务 | 方案B：现有 StrategyEngine 集成 |
|---|---|---|
| 触发 | `celery_app.py:74` `beat_schedule` 加 `crontab(minute='*/15')` | 现有 `evaluate`/`resolve` 是**按需同步调用**，无周期 |
| 周期保证 | ✅ celery beat 已接入，时区 `Asia/Shanghai`(celery_app.py:46)，已有 hourly 先例(`hourly-fault-prediction` L90) | ❌ 无定时，依赖外部调用 |
| 计算契约 | 需新建 task 函数组装上下文 | ✅ 已有 `ChargingContext`/`ChargingDecision` 完整契约 |
| 仲裁 | 需新建仲裁层 | ❌ 现有是单策略互斥（`resolve` 选一个 mode） |
| 流水落库 | task 内写 `energy_dispatch_plan`/`energy_flow_log` | ❌ 现有不持久化 |

**结论：方案A + 方案B 组合**——用 **celery beat 做周期触发**（方案A），复用 **现有 `ChargingContext`/`ChargingDecision` 契约 + `StrategyEngine`**（方案B 的抽象），**新增仲裁层**把"单策略选择"升级为"多策略并行仲裁"。这是最低改造成本、最高复用的路径。

### 4.2 接入步骤（设计层面）
1. 新增 `app/tasks/energy_tasks.py`，加入 `celery_app.py:30` `include` 列表 + `beat_schedule` 注册（`crontab(minute='*/15')`，对齐 96 节点）。
2. task 内：读 `station_energy_strategy` 配置 + 当前生效 `energy_price_template` → 组装 `ChargingContext`（字段已全部对齐 strategy_base.py:28）。
3. 调用新仲裁层（包裹 `StrategyEngine` + 多策略 `evaluate`），按 SPEC §4 优先级裁决产出合成 `ChargingDecision`。
4. 硬约束校验（变压器容量/SOC 底线/循环次数/防逆流）裁剪后，写 `energy_dispatch_plan`。
5. 读 `TelemetryPV`/`TelemetryBattery`/`TelemetryCharger` 聚合，写 `energy_flow_log`。
6. 把 `available_power_budget_kw` 下发给需求侧（见 4.3）。

### 4.3 与 charging_schedule 的功率预算协同接口

**数据流（供给侧 → 需求侧）**：
```
energy_tasks(15min)
  → 仲裁层算出下一窗口场站可用功率预算 available_power_budget_kw
  → 写入 energy_dispatch_plan.available_power_budget_kw
  → 传给 charging_schedule_service.generate_schedule(available_power_kw=...)
  → 需求侧在预算内 generate_schedule 排车 + 变压器容量约束(charging_schedule_service.py:6)
```

**协同契约要点**：
- `generate_schedule`(charging_schedule_service.py:54) 已接受 `available_power_kw` 入参，**接口现成**，无需改需求侧签名。
- 供给侧的"可用预算"= 变压器容量 + 储能增容额度 − 光伏直供占用 − 安全裕度（SPEC §3 硬约束）。
- 时序：供给侧 15min 周期先算预算 → 需求侧用预算排车。两层各管各的（供给侧"电从哪来"、需求侧"车怎么排"，SPEC §7 末尾）。
- `energy_dispatch_plan` 与 `charging_schedule_plans` 通过 `station_id` + `window_start` 关联，不做强 FK（计划表之间松耦合）。

## 6. 风险与不确定点

### 架构风险
1. **单策略 → 多策略仲裁的演进**（最大风险）：现有 `StrategyEngine.resolve`(strategy_engine.py:114) 是"手动抢占 + 单 mode 评估"，SPEC §4 要"多策略并行产出建议 + 仲裁器合成"。从互斥单选到并行仲裁是架构升级，仲裁层（同向取大/反向按优先级/权重模式）需 TDD 严格覆盖，避免回归现有 5 种模式行为。**建议仲裁层独立于现有 StrategyEngine 新建，作为上层编排，不破坏现有契约。**

### 数据/语义风险
2. **购电价 vs 对客售价混淆**：`energy_price_template.purchase_price`（买电成本）与 `EnergyPrice.price_per_kwh`（卖电给车主）是两条线，结算时不能混用。
3. **省级模板规则是示意值**：SPEC §5 四省时段/价差为示意，上线前须按最新电网文件校准（SPEC 明示）。
4. **充电负载预测缺失**：现有有光伏预测（`solar_forecast.py`），但**无充电负载预测**服务（SPEC §7 步骤1 要读"充电负载预测"）。动态增容/需量管理依赖负载预测，P1 可能需从 `charging_schedule` 车辆排班推导，或新建轻量预测——**不确定，需确认数据来源**。
5. **station 缺设备容量字段**：变压器/光伏/储能容量不在 `stations` 表（§1.7），放进 `station_energy_strategy` 承载。若已有场站配置存在别处，需先排查避免重复。

### 隔离契约风险
6. **team_id vs enterprise_id 不一致**：`charging_schedule.py` 用 `enterprise_id`(L52/L105) 隔离，但全站新端点须遵守 `team_id` 隔离契约（记忆 `[[team-isolation-contract]]`）。新六表统一 `team_id`，**不要**沿用 enterprise_id，否则重蹈"假隔离"漏洞。

### 执行链路不确定点（需后续确认）
7. **指令下发执行器**：SPEC §7 步骤3"下发功率指令"——现有有 `models/device_control_log.py`，但**是否有统一的设备控制下发服务（写光伏限功率/储能充放指令到实际设备）未确认**。本预研只到"产出计划/决策"，下发执行链路需单独排查 gateway/modbus/mqtt 模块。
8. **现货 96 节点数据源**：P3 的日前/实时价从哪来（省电力现货 API？手动？）未定，P3 仅预留结构不涉及。

### 已确认项（SPEC §10）
- ✅ 规则与价格解耦 + 版本化
- ✅ 15min×96 节点预留兼容
- ✅ 能量流可调 + 多策略并行
- ❓ 待丁哥确认：4 省起步 / 余电上网默认关 / 需量管理是否一期（影响 P1/P2 划分）
